# Acceptance Criteria

Each criterion is verifiable against a test fixture suite. v1 is complete when
all pass [DOC-01 Success criteria]. Fixtures use a local HTTP test server + recorded
responses; fixture configs set [CFG-042]=true so the local server is reachable
under the fail-closed egress policy — SSRF criteria (AC-025) run with it
false. Politeness tests use virtual time where possible [DEC-012].

## Ingestion & normalization

- AC-001: For each case in a 50-case normalization vector set (percent-encoding incl. reserved-octet preservation and unreserved decoding, uppercase hex, default ports, dot-segments, fragments, IDN, uppercase hosts, empty paths), output matches the expected identity exactly; function is pure (repeat calls identical).
- AC-002: Seeds that are unparseable, have a disallowed scheme, or contain userinfo abort startup with exit code ≠ 0 before any network I/O.
- AC-003: A page containing 100 duplicate links yields exactly one new URL Record.
- AC-004: With scope_mode=SEED_DOMAINS, a link from sub.example.org to example.org is IN_SCOPE; to other.org is OUT_OF_SCOPE and never fetched.
- AC-005: Startup with scope_mode=PREFIX_LIST where a seed matches no entry of [CFG-039] aborts with exit code ≠ 0 before any network I/O [V-4].
- AC-006: With [CFG-006]=2, exactly two page successes per Registrable Domain are fetched; further in-scope discoveries on that domain are recorded ST-190/`CAP_REACHED` and never fetched, other domains are unaffected, and ST-190 audit records do not consume the [CFG-005] budget [FR-005]. The bound holds even when all discoveries enqueue before the first fetch on the domain completes (dispatch-time gate [FR-011(e)]). **Important: the enqueue-time global cap [CFG-005] counts all URL Records in non-EXCLUDED states (including ST-100), while the per-domain check [CFG-006] only counts successes+inflight in {ST-130, ST-140, ST-110, ST-120} — ST-100 is excluded from the per-domain check, so a domain with many queued URLs but no in-flight/successful fetches can still accept new discoveries at enqueue time; the dispatch-time gate enforces the per-domain bound authoritatively.**

- AC-007: With [CFG-006]=2, [CFG-005]=20, and a domain having 15 URL Records enqueued as ST-100 (queued but not yet dispatched) with zero successes and zero inflight records in {ST-130,ST-140,ST-110,ST-120}, the enqueue-time per-domain budget check does NOT trigger (ST-100 is excluded from the per-domain check), allowing all 15 to be ingested as ST-100. The dispatch-time gate [FR-011(e)] then enforces the per-domain bound: after 2 dispatches succeed and complete ( establishing 2 page successes), the 3rd dispatch attempt moves the record to ST-190/`CAP_REACHED`. This test verifies that (a) a domain with many ST-100‑queued URLs but no in‑flight/successful fetches can accept new discoveries at enqueue time, and (b) the dispatch-time gate authoritatively enforces the per-domain cap regardless of enqueue-time ordering.
 
- AC-008: With [CFG-006]=2, [CFG-005]=20, and a domain having 5 URL Records enqueued as ST-100 (queued but not yet dispatched) with zero successes and zero inflight records in {ST-130,ST-140,ST-110,ST-120}, the enqueue-time per-domain check does NOT trigger, allowing all 5 to be ingested as ST-100 because neither a candidate's own ST-100 state nor ST-100 records in general count toward successes(D) or inflight(D) [FR-005(1)(B)]. At dispatch time the gate [FR-011(e)] evaluates the same sum, but that sum is not static: [T-1] moves a dispatched record ST-100→ST-110 (inflight(D) +1) and [T-2] completion moves it to ST-140 (inflight(D) −1, successes(D) +1). The gate therefore does NOT trigger on the first two dispatch attempts — before them successes(D)+inflight(D) is 0 and then 1, both < [CFG-006] — but once both complete successes(D)=2, inflight(D)=0, and the third dispatch attempt is excluded: the record moves ST-100→ST-190/`CAP_REACHED`, no [T-1] commits, no request is sent, and the sum never exceeds [CFG-006] [FR-005(2)], [AC-007], [AC-078]. This test verifies that (a) the dispatch-time gate enforces the per-domain bound as soon as the domain accumulates sufficient successes+inflight in {ST-130,ST-140,ST-110,ST-120}, and (b) prior to that, ST-100-queued records freely progress to ST-110 for dispatch, consistent with the note in FR-005(2).
 
 ## Politeness, robots & scheduling

- AC-009: At dispatch time the robots gate [FR-011(d)] is evaluated on ST-100 records: a URL whose Host's robots verdict is ALLOW is admitted for dispatch; a URL whose Host's robots verdict is DISALLOW moves to ST-190/`ROBOTS_DISALLOW` and is never fetched. The DISALLOW exclusion fires at selection time (before [T-1]) and shrinks the candidate set (same termination as the dispatch-time domain-cap gate [FR-011(e)] exercised by AC-007/AC-008: ST-190 is terminal). Because the record is still ST-100, it holds no units and none are released [R-051]; only a verdict change after [T-1] takes the ST-110→ST-190 send-time path [R-054], which releases the held units exactly once [R-051].
- AC-034: With [CFG-005]=5 and [CFG-006]=2, enqueuing 5 URL Records as ST-100 on a domain with zero successes and zero inflight records in {ST-130,ST-140,ST-110,ST-120} triggers the enqueue-time global cap [CFG-005] check: the 6th discovery on that domain is recorded ST-190/`CAP_REACHED` and never enqueued, since the global cap counts all non-EXCLUDED states system-wide, including ST-100. The per-domain check [CFG-006] does NOT trigger (ST-100 excluded), but the global cap prevails. Because [CFG-005] is system-wide, a 6th discovery on any other domain is likewise capped even though that domain holds no records; it is the per-domain check [CFG-006] that leaves other domains unaffected when the global cap is not reached [FR-005(1)(A)]. After 2 of the queued dispatches succeed and complete on that domain, the per-domain gate then enforces [CFG-006] independently on the remaining queued records.
- AC-010: With two workers and CFG-007=5000ms, request starts to one host are ≥ 5000 ms apart across 20 fetches (start-to-start).
- AC-011: Per-host inflight never exceeds CFG-009 under any fixture — counting in-flight HTTP tasks (one unit per dispatched record from [T-1] to [T-2] spanning its hops, plus robots exchanges [DOC-00], [R-212]); global inflight never exceeds CFG-010 — counting in-flight HTTP tasks (one unit per dispatched record from [T-1] to [T-2] spanning its hops, plus robots exchanges) [DOC-00], [R-212]. Per the release-before-acquire protocol [R-131], a task holds at most one Host unit at any time; redirect hops release the previous Host unit before acquiring the next, so per-host inflight counts concurrent tasks, not individual HTTP requests.
- AC-035: With [CFG-009]=1, a single fetch task that follows a redirect chain making 3 hop requests to the same Host never causes per-host inflight to exceed 1; the release-before-acquire protocol [R-131] ensures the per-Host unit is released before the next hop's gates are evaluated, so concurrent tasks (not individual HTTP requests) are counted. This verifies that per-host inflight counts tasks consistent with global inflight [CFG-010], and that no Host slot leaks occur during redirect chains.
- AC-012: robots.txt Disallow for UA group blocks matching URLs → ST-190/ROBOTS_DISALLOW; the longest matching rule value wins (wildcards count as one character), with Allow winning an exact-length tie per [R-101]; `*` ignored when a matching token group exists. Rule matching per [R-101]: values match byte-wise, case-sensitively, against path plus `?query` when present (`Disallow: /*?` blocks a URL with any query); a terminal `$` anchors the end; a `*` matches any sequence incl. empty; no group matches and no `*` group exists ⇒ all URLs allowed; an empty `Disallow` value ⇒ allow all.
- AC-013: robots.txt returning 503 defers ALL host fetches; retry after backoff succeeds once robots returns 200; no page was fetched during deferral; the Host's `robots_state` is DEFERRED throughout the deferral and OK once the 200 is parsed [R-106]. A robots final response outside 2xx/4xx and outside the followable redirect set — e.g. a spurious 304 (the request carries no validators) or a 300 — likewise defers the Host (fail closed) [DOC-08 §2.3].
- AC-014: Crawl-delay=12 s honored over CFG-007=5000 ms (unit normalization per [DOC-08 §4] — the seconds-valued Crawl-delay must dominate the ms-valued defaults); Retry-After=120 s overrides backoff when larger.
- AC-015: A redirect whose hop target is disallowed by the target Host's robots.txt terminates the chain with outcome=PERMANENT and error_class=ERR-017; the source URL → ST-180; the target is never fetched; the hop appears in the source's `redirect_chain` [R-131].
- AC-016: Between dispatch [T-1] and request send, a robots cache refresh to DISALLOW moves the record ST-110→ST-190/`ROBOTS_DISALLOW` and releases its units; a refresh to UNKNOWN (Host deferred) compensates the record back to ST-100. In both cases no request is sent, no fetch_event is written, and the [T-1] attempts increment is rolled back [T-5], [R-053], [R-054]; no request is sent while the Host is deferred.
- AC-017: A redirect hop whose target Host is robots-deferred (verdict UNKNOWN) aborts the chain with outcome=RETRYABLE and error_class=ERR-010; the source → ST-150; no request is sent to the target Host during deferral [R-131].
- AC-018: With two due candidates on different Hosts — priorities 900 and 100, the lower-priority one due earlier — the higher-priority candidate is dispatched first: `due_at_mono` never orders already-due work [FR-010].
- AC-019: On robots.txt cache TTL expiry [CFG-008] with a cached entry, gate queries keep using the previous rules while the revalidation fetch is in flight; a 2xx revalidation swaps in the new rules atomically; a failing revalidation defers the Host [R-104]. Concurrent gate queries during any in-flight acquisition never issue a second robots request for the same Host [R-105].

## Fetching & errors

- AC-020: 6-hop redirect chain with CFG-017=5 stops at hop 5; outcome=PERMANENT with error_class=ERR-011 recorded [R-130]; the un-followed 6th `Location` target is recorded in the source's `redirect_chain` [R-133].
- AC-021: Redirect loop (A→B→A) detected at first repetition — the hop target equal to the original identity counts [R-132]; the refused loop-back hop target appears in the source's `redirect_chain` (a refused hop target, not the requested-URL prefix) [R-133].
- AC-022: Payload of CFG-016+1 bytes aborted mid-stream; nothing persisted for it; ERR-007 recorded. A gzip body whose *decoded* size exceeds [CFG-016] aborts identically (the running byte count is checked during decode) — PERMANENT, ERR-007, no partial payload persisted [R-310].
- AC-023: gzip body decoded before hashing; stored hash equals SHA-256 of decoded bytes.
- AC-024: 429 with Retry-After honored; attempts stop at CFG-020; then DEAD, with `urls.last_error_class` = the budget-exhausting outcome's class (the DEAD branch records it durably [DOC-13 §3], [T-2]). A 429 `Retry-After` larger than [CFG-035] is honored unclamped [DOC-13 §3]. A yes-once class failing twice — e.g. two ERR-003 outcomes with [CFG-020]=5 — reaches DEAD at the second occurrence [R-232]; after a success and a recrawl promotion ([R-052] attempts reset), the class is eligible for one retry again.
- AC-025: Connection to a host resolving to 127.0.0.1 (from a page link) is blocked with ERR-004 and never connects.
- AC-026: A redirect chain crossing into a second host waits for that host's politeness window before each hop request [R-131]; on success the final target has its own URL Record with depth equal to the source's [R-062], and the chain is persisted on the source's fetch_events row [R-133]; per [R-051]/[R-131] the task holds at most one Host unit at any time — the source Host's unit is released when its redirect response is received (unit transfer) and the final hop's Host unit is released exactly once at completion [T-2], so no Host slot leaks. A deadlock fixture with [CFG-009]=1 on two Hosts A and B and two concurrent cross-host chains A→B and B→A completes both chains: each releases its held unit before waiting, so the waits cannot cycle [R-131]. If the final target's identity already has a terminal record (e.g. ST-190/`CAP_REACHED`), the upsert overwrites it with the fetch outcome [R-062] — a completed, gate-verified fetch is not automated re-activation [DOC-13 §4], and `last_error_class` is cleared on success; if it is independently in flight ({ST-110, ST-120}), its state and `attempts` are untouched and the chain records `last_seen_at` plus its `pages` row only. On chain success both page rows (source's and target's) commit in one [T-2].
- AC-027: With robots.txt persistently returning 5xx for ≥ [CFG-040], gated URLs (ST-100 and ST-150) transition to ST-190/`ROBOTS_UNKNOWN_TIMEOUT` and are never fetched [R-103]; the sweep fires at the threshold expiry itself (a scheduler wake source [R-211]). Records entering gated states after the threshold passed (a new discovery, a ST-140→ST-100 recrawl promotion) are excluded by the next sweep evaluation [R-103]; swept records retain no stale `next_attempt_mono` (cleared whenever a record leaves ST-150 [R-103], [DOC-12 §1]).
- AC-028: A 3xx response with a missing or unparsable `Location` header yields outcome=PERMANENT with error_class=ERR-011; no follow occurs [DOC-09 §4].
- AC-029: With [CFG-028]=false, fetching a non-HTML type (e.g. `application/pdf`) stores no blob, records error_class=ERR-008, and the URL → ST-180 (the effective allowed list is empty); with [CFG-028]=true the payload is stored and no parse artifacts are produced [R-143].

## State machine & durability

- AC-030: kill -9 during ST-110 (dispatched, request-sent status unknown) or ST-120 leaves the record resumable; after restart it is reclassified per the crash rule [DOC-13 §5], [R-060]: attempts preserved, state ST-150 with backoff-scheduled retry (ST-180 when the budget was exhausted by the crash — from either state), no politeness violation (persisted next_allowed_fetch_at respected), and `inflight` rebuilt to 0.
- AC-031: kill -9 after blob write but before T-2 commit leaves an orphan blob that the retention sweep removes; no pages row references a missing blob ever (invariant scan passes). While a fetch attempt is in flight (fixture-held response), a sweep falling due in that window performs no blob deletions even for unreferenced blobs — the attempt may still commit a pages row referencing its staged blob, or, via a 304 completion [R-144], re-affirm a hash whose last referencing row the sweep just deleted; after the attempt settles, a later sweep collects genuine orphans [R-502], [DOC-11 §6].
- AC-032: Full restart with unchanged config produces no duplicate work [NFR-012]: no URL Record is re-created ({ingested} unchanged); config-seed re-ingestion follows rediscovery semantics [FR-051], [FR-006] — `last_seen_at` updates, and scheduling refreshes only if [CFG-021]=true — and counts solely toward urls_discovered_total{duplicate} [DOC-15 §1].
- AC-033: Replay of a recorded fixture produces identical fetch decision sequences across three runs [NFR-006].

## Extraction & storage

- AC-040: Known HTML fixture yields exact expected artifact JSON (title, canonical, headings, main_text, outlinks) byte-identically across runs; a variant fixture whose valid relative `<base href>` overrides the final URL resolves its outlink candidates against that base ([R-021], [FR-042]).
- AC-041: Page with meta robots=nofollow yields zero ingested anchor candidates but stores the page; a companion `noindex,nofollow` fixture sets `noindex=true` on the `pages` row and records both directives in the artifact after extraction [T-4]. A `<title>` fixture observes the artifact title in `pages.title` after [T-4].
- AC-042: Byte-identical payload from two different URLs shares one blob file; both pages rows reference its hash. Two URLs on different Hosts returning byte-identical HTML containing relative links additionally hold distinct page_artifacts rows, keyed `(payload_sha256, final_url_identity)` — mirrors share bytes, never each other's resolved outlinks [DOC-11 §1].
- AC-043: Retention job deletes pages older than CFG-027 including blobs, never leaving dangling references mid-sweep; a blob/artifact row still referenced by any surviving pages row is retained even when individual referencing pages are deleted. With [CFG-027]=0, [CFG-033]=0, or [CFG-043]=0, the corresponding sweep step deletes nothing (keep forever [DOC-11 §6]). Seed records (`is_seed=true`) are never deleted by the DEAD/EXCLUDED step, however stale [FR-006], [DOC-11 §6].
- AC-062: A fixture page whose filtered, deduplicated candidates exceed the per-page cap — e.g. 1200 distinct in-scope anchor hrefs — ingests exactly 1000 URL Records (the first 1000 in document order), sets `truncated=true` on its artifacts, and counts the 200 overflow candidates in urls_discovered_total{dropped} [R-159], [DOC-15 §1].

## Operations

- AC-050: SIGTERM triggers drain: no new dispatches, in-flight fetch tasks complete within their bounded timers (per-hop [CFG-015]; inter-hop waits ≤ [CFG-035] [R-131]), exit code 0, run_summary emitted.
- AC-051: Startup with 1M-record store reaches first fetch within 60 s [NFR-005].
- AC-052: All metrics counters appear after exercise; state_transitions_total contains only legal transition pairs [DOC-07 §2] and labels every record-creating transition with `from=creation` — specifically creation→ST-100 [FR-003] (new URL Record ingress), creation→ST-190 [FR-004] (ingestion filter outcomes only: out-of-scope, trap filters, depth limit, enqueue-time cap), and creation→ST-130/ST-150/ST-180 [R-062] (redirect final-target upsert creations) — while all other transitions bear their own `from` label per the state machine (e.g. dispatch, robots re-check, reset); urls_discovered_total's four buckets partition every ingestion event exactly (`duplicate` fires for a rediscovery and for an upsert onto a pre-existing record [DOC-15 §1]), and bytes_downloaded_total includes a body discarded by [ERR-008] and the pre-abort bytes of an [ERR-007] body.
- AC-053: Operator reset of a DEAD URL via the runtime API returns the record to ST-100 with attempts=0, last error class cleared, and any stale `next_attempt_mono` cleared [DOC-13 §4], emits the ST-180→ST-100 transition metric [DOC-15 §1], and writes an audit log entry [DOC-13 §4].
- AC-054: With [CFG-034] bound to a non-loopback address, the mutating operator actions (seed injection, DEAD reset, drain trigger) are disabled, a startup WARN is logged, and /healthz and /metrics remain available [R-406].
- AC-055: A redirect hop whose target Host's Crawl-delay implies a politeness wait > [CFG-035] aborts the chain with outcome=RETRYABLE and error_class=ERR-018; the source → ST-150; no Host concurrency unit is held during any politeness or capacity wait [R-051], and no fetch worker is held for an over-threshold wait — the chain aborts instead (waits ≤ [CFG-035] do hold the task's worker, never a Host unit); `next_attempt_mono` is floored at the target Host's window opening; if the window never opens within the retry budget, the URL reaches ST-180 [R-131], [DOC-13 §3].
- AC-056: Hop-target acceptance [R-130], [R-131], one fixture per case: (a) a relative `Location` value resolves against the hop URL to the correct absolute target (chain follows it); (b) a `Location` with a non-http(s) scheme or userinfo yields outcome=PERMANENT, error_class=ERR-011, no follow, and the refused target appears in the source's `redirect_chain` [R-133]; (c) a hop target matching a [CFG-037] pattern yields outcome=PERMANENT, error_class=ERR-019, source → ST-180, target never fetched, hop recorded in `redirect_chain`.
- AC-057: With scope_mode=SEED_DOMAINS and an IP-literal seed (e.g. `http://127.0.0.1/`, served by the local fixture server under [CFG-042]=true [R-405]), other URLs on the same IP literal are IN_SCOPE and every named host is OUT_OF_SCOPE — scope matching is lexical over Registrable Domains, never DNS-dependent [DOC-00]; `[2001:0DB8::1]` and `[2001:db8::1]` normalize to one URL Identity [R-003].
- AC-058: Runtime seed injection of a URL violating [FR-002] (bad scheme, unparseable, userinfo) or, with scope_mode=PREFIX_LIST, matching no [CFG-039] entry [V-4] returns an error, does not abort the process, and records ST-190/`OUT_OF_SCOPE` only for the [V-4] case with [CFG-038]=true ([FR-002] violations record nothing — no identity, no reason code [FR-006]). A valid injection behaves identically to a config seed [FR-006] — including setting `is_seed=true` idempotently on a pre-existing record (scope-set expansion [DOC-06 §4], priority recomputed [DOC-12 §2]) without re-activating DEAD or EXCLUDED records [FR-051]; with SEED_DOMAINS or SEED_HOSTS, injecting a well-formed seed on a new domain/Host ingests it IN_SCOPE and expands the scope set [R-032], exactly as a new config seed does.
- AC-059: A 304 with no usable stored payload triggers exactly one full unconditional refetch completing the same fetch attempt (no extra `attempts` increment): (a) blob removed by retention — the refetch stores a fresh payload and the attempt succeeds; (b) first-fetch 304 (no validators sent) — if the refetch also returns 304, the outcome is PERMANENT/ERR-014 [R-144].
- AC-060: A configuration violating any validation rule [V-1]–[V-7] — e.g. [CFG-015] < [CFG-014] [V-2], an empty [CFG-003] [V-6], a [CFG-018] not matching the UA Token pattern or an invalid [CFG-019] email [V-5], [CFG-044] > [CFG-040] [V-7], any out-of-range value [V-1] — aborts startup with exit code ≠ 0 before any network I/O, and the error identifies the offending key [DEC-011].
- AC-061: Redirect final-target failure upserts [R-062]: (a) a chain completing with a RETRYABLE outcome whose final target has no pre-existing record creates it in ST-150 with `next_attempt_mono` equal to the source's; (b) a RETRYABLE-outcome upsert onto a pre-existing terminal record whose `attempts` ≥ [CFG-020] (e.g. a budget-exhausted DEAD record) lands in ST-180 — after any upsert, no ST-150 record holds `attempts` ≥ [CFG-020] [DOC-12 §1]; (c) a chain aborted before sending to its final target (e.g. an ERR-017 robots-blocked hop) creates no target URL Record — the failure and `redirect_chain` are recorded on the source only; (d) failure upserts set the target's `last_error_class` to the outcome's class, success upserts clear it, and a class set by a RETRYABLE upsert is cleared again by the target's own next successful completion — after that completion the column is NULL [T-2], [R-062]; (e) upsert-overwrite state changes (e.g. ST-190/`CAP_REACHED`→ST-130, ST-180→ST-150, ST-140→ST-180) are legal transitions listed in [DOC-07 §2] and appear in state_transitions_total — a same-state landing (ST-130→ST-130, ST-150→ST-150, ST-180→ST-180) emits no transition metric [DOC-07 §2], no upsert lands in ST-190 (every ST-190 target is overwritten), an upsert leaving ST-190 clears `exclude_reason`, and a landing outside ST-150 clears `next_attempt_mono`; (f) a yes-once RETRYABLE class (ERR-003/ERR-013) is appended to the target's `once_retried_classes` exactly as to the source's, and an already-listed class makes the outcome PERMANENT for the target [R-062], [R-232]; (g) a pre-existing target record keeps its own `depth`, `discovered_from`, `source_run_id`, and `is_seed` across an upsert overwrite — the creation-time fields are written only at creation, and only the fields [R-062]/[T-2] name change [R-062].
- AC-063: A response whose header block exceeds 64 KiB is rejected with outcome=PERMANENT and error_class=ERR-016; no payload is persisted, no fetch_worker is held, and the URL Record moves to ST-180 [DOC-16 §3], [DOC-09 §4].
- AC-064: A discovery whose query string contains a parameter name matching any [CFG-029] glob pattern is recorded ST-190/`TRAP_PARAM` and never fetched [DOC-06 §5 filter 2]. Parameter names are extracted by splitting the query on `&`; a name is the substring before the first `=` or the whole token when it contains no `=`. Globs match the whole name case-sensitively with `*`/`?`/`\` per [R-043]: `s*d` matches `sid`, `SID` does not, and an (implicitly anchored, whole-string) `sid` pattern does not match `sessionid`.
- AC-065: On a given Host, once [CFG-030] URL Records share the same path shape (each maximal digit run in the normalized path replaced by a single `N`, query excluded), the next candidate with that shape is recorded ST-190/`TRAP_PATH_BUDGET` and never fetched [DOC-06 §5 filter 3].
- AC-066: A discovered URL whose depth exceeds [CFG-004] is recorded ST-190/`DEPTH_LIMIT` and never fetched; seeds have depth 0, discovered URLs have depth = parent depth + 1 [DEC-009] [DOC-06 §5 filter 4].
- AC-067: A discovered URL matching any [CFG-037] glob pattern is recorded ST-190/`BLOCKLIST` and never fetched [DOC-06 §5 filter 1]; matching is against the whole normalized URL, case-sensitively, with `*`/`?`/`\` per [R-043] (e.g. `https://example.com/private/*` matches its subpaths, while a bare `example.com` matches no URL). A redirect hop target matching the blocklist terminates the chain PERMANENT/ERR-019, source → ST-180, target never fetched, hop recorded in `redirect_chain` [R-131].
- AC-068: A redirect chain whose hop target leaves scope (URL's Registrable Domain not in the seed set) terminates that hop with outcome=PERMANENT and error_class=ERR-015; the source URL → ST-180, the out-of-scope target is never fetched, and the refused hop appears in the source's `redirect_chain` [R-030], [DOC-09 §4].
- AC-069: A redirect hop target that fails SSRF checks ([R-400]) terminates the chain with outcome=PERMANENT and error_class=ERR-004; the source URL Record → ST-180, the target is never fetched, and the Host of the redirecting hop that supplied the `Location` (the referring hop) is flagged `suspicious=true` [R-402]. The `suspicious_hosts` gauge reflects the count [DOC-15 §1].
- AC-070: A redirect hop whose target robots verdict changes from ALLOW to DISALLOW while the task waits for the target Host's politeness/capacity window is refused at the pre-send re-check: outcome=PERMANENT, error_class=ERR-017, source → ST-180, no request sent to the target, hop recorded in `redirect_chain` [R-131]. A change to UNKNOWN (target Host deferred) instead aborts RETRYABLE/ERR-010 with the source → ST-150. No request is sent in either case.
- AC-071: An HTML fixture whose title/description/meta text is large enough to push the artifacts JSON over 2 MiB still commits an artifacts row ≤ 2 MiB with `truncated=true`, truncating in the fixed [DOC-10 §3] order (headings, main_text, outlinks, then the remaining variable-length strings); `word_count` matches the *stored* main_text after truncation [DOC-16 §3].
- AC-072: A successful 2xx response carrying `Cache-Control: no-store` is stored and extracted normally (payload in Content Store, artifacts committed in [T-4]) but is never scheduled for recrawl: [T-2] leaves `urls.due_at_mono` NULL, the ST-140→ST-100 due-time promotion [DOC-12 §1] is suppressed, and the record remains ST-140 (terminal for its fetch cycle [DOC-07 §2]) until a rediscovery refresh ([CFG-021]=true [FR-051]) re-admits it [R-221] (the operator DEAD reset applies only to ST-180 records); by contrast a plain 2xx (or a 304) success installs a recrawl due time and the record returns to ST-100 when due [FR-050].

- AC-099: A valid `<base href>` is the resolution base for the page's relative links; only the `<base href>` value itself — not the page's links — is resolved against the final URL [R-020], [R-021], [FR-042], [AC-040]. With a fixture page whose final URL (post-redirect, so it differs from the requested identity [R-020]) is `https://example.org/a/b/page` and whose HTML contains `<base href="../assets/">` plus `<a href="item">`, the base value resolves against the final URL per RFC 3986 §5 to `https://example.org/a/assets/`, and the relative link MUST be ingested as `https://example.org/a/assets/item` — not `https://example.org/a/b/item`, which is what resolving the link against the final URL would produce. A companion fixture with an invalid `<base href>` (e.g. `javascript:alert(1)` or `ftp://example.org/`) MUST ignore the base and resolve its `<a href="item">` against the final URL to `https://example.org/a/b/item` [R-001], [R-002]. An implementation following the former [R-021] clause "A relative `href` is first resolved against the final URL per RFC 3986 §5" literally — applying it to page links instead of to the `<base href>` value — ingests the first fixture's link as `https://example.org/a/b/item`, fails this test, and contradicts [R-021]'s own override clause, [FR-042] and [AC-040], even though it happens to produce the correct identity for the invalid-base fixture.

- AC-100: The dispatch-time per-domain gate [FR-011(e)] evaluates a live sum successes(D)+inflight(D) that each dispatch and completion updates; it is not disabled for a fixed number of dispatch attempts merely because the candidates are ST-100 at enqueue [FR-005(2)], [AC-007], [AC-008], [AC-078].
